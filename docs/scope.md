

## 1. Problem Statement

KijaniKiosk has been developed through multiple stages of DevOps engineering, but the deployment process still requires a production-approaching multi-environment workflow with controlled promotion. The current system needs an isolated staging environment, automated deployment and validation, monitoring, and integration with the existing serverless receipt chain. This capstone extends the existing KijaniKiosk platform into a reproducible delivery system where changes can be deployed to staging, validated automatically, and promoted to production only after successful verification.

## 2. Selected Track

**Track A — Infrastructure-First**

The project focuses on extending KijaniKiosk into a multi-environment, monitored, production-approaching system using Infrastructure as Code, configuration management, Kubernetes, Jenkins CI/CD, monitoring, and the existing serverless receipt chain.

## 3. In-Scope Components

1. **Staging Infrastructure:** Provision the `kijani-staging` Kubernetes namespace using Terraform and configure the environment using Ansible, keeping it isolated from the `default` production namespace.

2. **Kubernetes Application Deployment:** Deploy `kk-payments` to staging using the same Deployment manifest used for production, with environment-specific ConfigMaps providing separate configuration such as `DB_HOST`.

3. **CI/CD Pipeline:** Extend Jenkins so that a merge to `main` automatically deploys KijaniKiosk to staging, executes a smoke test, and presents the production approval gate only after the smoke test succeeds.

4. **Monitoring:** Commit a monitoring signal for `kk-payments` to the repository, using a Prometheus alert rule that detects a meaningful application health condition such as an error rate exceeding 5% for two minutes.



## 4. Out of Scope

* **Multi-region infrastructure:** Deploying KijaniKiosk across multiple geographic regions is excluded because the capstone focuses on demonstrating a reproducible multi-environment delivery workflow rather than global high availability.

* **Complete enterprise production hardening:** Full enterprise security, disaster recovery, and high-availability implementation are outside the capstone scope. Production gaps identified during the project will instead be documented with specific recommended remediations.

## 5. Success Criteria

The project will be considered successful when the following can be demonstrated:

* A `kijani-staging` namespace can be provisioned reproducibly using Terraform and configured using Ansible.
* `kk-payments` runs successfully in staging with configuration that differs from the production environment.
* A merge to `main` triggers the Jenkins pipeline and automatically deploys the application to staging.
* The staging smoke test passes before the production approval gate becomes available.
* A production deployment can be completed after an approved promotion.
* A committed monitoring rule provides a measurable health signal for `kk-payments`.
* A receipt generated by staging `kk-payments` reaches the `kk-payments-receipts-staging` bucket and triggers the serverless receipt chain.
* The repository contains sufficient documentation for another engineer to understand and reproduce the system.

## 7. Project Boundary

The capstone builds on the existing KijaniKiosk codebase and Week 1–10 work. The focus is not to create a new application, but to extend the existing system into a reproducible, automated, monitored deployment workflow. The final implementation should demonstrate the infrastructure, delivery, runtime, and intelligence/observability layers required by the selected track.

**Expected outcome:** A new engineer should be able to understand the architecture, reproduce the staging environment, deploy the application, run the validation process, and understand the path from staging to production using the repository documentation.
